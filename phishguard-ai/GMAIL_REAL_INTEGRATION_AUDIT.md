## EXECUTIVE SUMMARY

An exhaustive investigation of the PhishGuard AI codebase was conducted across frontend, backend, database models, worker queues, and configuration layers. 

**The primary finding is conclusive:**  
The existing Gmail integration in PhishGuard AI is **100% simulated (dummy/mock)** in its connection and synchronization workflows:
1. The frontend "Connect Gmail" button does **not** initiate an OAuth 2.0 handshake with Google; it merely opens a modal that captures an email and optional password, immediately posting to a backend mock endpoint.
2. The backend generates **synthetic email fixtures** with hardcoded strings (`_generate_seed_gmail_messages`) and precomputes heuristic risk scores using simple substring searches (`servehttp`, `Immediate Wire`).
3. There are **no Google OAuth libraries**, no Google API client SDKs, no Google Cloud Pub/Sub client libraries, and **zero Google OAuth credentials** (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`) defined anywhere in `Settings`, `.env`, or `.env.example`.
4. The background mail-flow webhook handler for Google Workspace (`mail_flow_service.py`) operates on a fundamentally flawed premise: it expects raw email content in the Pub/Sub payload. In reality, Gmail Pub/Sub only transmits mailbox change metadata (`emailAddress`, `historyId`).
5. Quarantine actions currently only alter an internal database column (`analysis_status = "quarantined"`); no API call is made to Gmail to remove the `INBOX` label, apply a quarantine label, or move threats to Spam/Trash.

However, the **downstream email analysis pipeline** (`EmailParser`, `HeaderAnalyzer`, `URLAnalyzer`, `AttachmentAnalyzer`, `IOCExtractor`, `RiskScorer`, and Celery worker `execute_email_analysis`) is **fully functional, production-grade, and real**. 

A genuine Gmail integration can be built cleanly by connecting official Google OAuth 2.0 authorization, Gmail REST API v1, Cloud Pub/Sub webhooks, and Gmail History API synchronization directly into this existing pipeline.

### 5.1 OAuth Scope Evaluation & Security Analysis
To satisfy the requirements of:
1. Inbox monitoring
2. Message retrieval
3. Quarantine (removing from Inbox, tagging, or trashing)
4. Restoration (restoring to Inbox)

We must evaluate the candidate scopes:

| Scope | Description | Pros | Cons | Verdict |
| :--- | :--- | :--- | :--- | :--- |
| `https://www.googleapis.com/auth/gmail.readonly` | Read-only access to messages and metadata | Non-sensitive or sensitive (lower audit overhead) | **Cannot modify labels, cannot archive, cannot quarantine** | Insufficient |
| `https://www.googleapis.com/auth/gmail.modify` | Read, compose, send, and modify labels / trash | **Allows reading raw messages AND modifying labels for quarantine** | Classified by Google as a **Restricted Scope**; requires CASA Tier 2 validation for public production | **RECOMMENDED & REQUIRED** |
| `https://mail.google.com/` | Full access to Gmail account | Can do everything | Excessive privileges; severe security risk | **REJECTED** |

#### Restricted Scope Implications (`gmail.modify`):
* **Internal / Testing Mode:** In Google Cloud Console, an app in "Testing" mode allows up to 100 explicitly added test Google accounts to authorize without third-party audit. This is ideal for academic development, demonstration, and FYP evaluation.
* **Production Deployment:** Requires Google OAuth App Verification, Cloud Application Security Assessment (CASA Tier 2), privacy policy, and security assessment.
* **Least Privilege Principle:** `gmail.modify` is strictly narrower than `mail.google.com` while providing the exact capability required to execute quarantine and label management.

### 5.2 Real Message Ingestion & History API Synchronization Flow
1. **Initial Watch Setup:**
   - When a user authorizes, the backend calls:
     ```python
     service.users().watch(
         userId='me',
         body={
             'topicName': f'projects/{settings.GOOGLE_CLOUD_PROJECT}/topics/{settings.GMAIL_PUBSUB_TOPIC}',
             'labelIds': ['INBOX'],
         }
     )
     ```
   - Google returns `historyId` and `expiration` timestamp (watch expires every 7 days; requires background renewal cron).
2. **Push Event Reception:**
   - Cloud Pub/Sub sends a `POST` request to `/api/v1/webhooks/google-workspace`.
   - The payload contains:
     ```json
     {
       "message": {
         "data": "eyJlbWFpbEFkZHJlc3MiOiAidXNlckBleGFtcGxlLmNvbSIsICJoaXN0b3J5SWQiOiAiMTIzNDU2In0="
       }
     }
     ```
   - Backend decodes `message.data` to extract `emailAddress` and `historyId`.
3. **Delta Sync via History API:**
   - Backend looks up the `GmailIntegration` record for `emailAddress`.
   - Queries `service.users().history().list(userId='me', startHistoryId=integration.last_history_id, historyTypes=['messageAdded'])`.
   - For every `messageAdded` event in `INBOX`:
     - Fetches raw RFC-822 email via `service.users().messages().get(userId='me', id=msg_id, format='raw')`.
     - Base64-url decodes the raw email bytes.
     - Calls `mail_flow_service.ingest_raw_message(raw_content=raw_email, source_type="gmail_sync", ...)` which directly leverages the existing `EmailParser` and dispatches Celery `analyze_email_task`.
   - Updates `last_history_id = historyId`.

### 5.3 Real Gmail Quarantine & Restore Workflow
1. **Quarantine Action:**
   - When analysis completes and threat level is `Critical` or `Malicious` (or when SOC Analyst manually clicks Quarantine):
   - Check if `PhishGuard-Quarantine` label exists on user's mailbox; if not, create it via `users().labels().create()`.
   - Call `service.users().messages().modify(userId='me', id=gmail_message_id, body={'removeLabelIds': ['INBOX'], 'addLabelIds': [quarantine_label_id]})`.
   - Update `GmailMessage.analysis_status = "quarantined"` and `Email.analysis_status = "quarantined"`.
2. **Restore Action:**
   - Call `service.users().messages().modify(userId='me', id=gmail_message_id, body={'addLabelIds': ['INBOX'], 'removeLabelIds': [quarantine_label_id]})`.
   - Update status back to `restored`.

## 8. SECURITY & TENANT-ISOLATION PLAN

1. **Strict Multi-Tenant Isolation:**
   - Every `GmailIntegration` and `GmailMessage` record contains both `organization_id` and `user_id`.
   - All backend queries strictly filter by `organization_id == current_user.organization_id` AND `user_id == current_user.id`.
   - Users can only view, sync, or quarantine emails from their own connected Gmail account. Organization Security Admins can view threat aggregated metrics across the organization without accessing raw private email bodies without explicit role grants.
2. **Encryption of OAuth Tokens at Rest:**
   - Access tokens and refresh tokens must never be written to the database in plaintext.
   - Utilize cryptography's `Fernet` symmetric encryption keyed by `settings.ENCRYPTION_KEY`.
   - Decryption occurs only in-memory immediately prior to issuing authenticated Google API requests.
3. **State & CSRF Protection During OAuth:**
   - OAuth `state` parameter must be cryptographically random (`secrets.token_urlsafe(32)`), signed with a HMAC timestamp, and stored in Redis/session with a 10-minute expiration.
   - State must bind `user_id` and `organization_id` to prevent cross-account injection attacks.
4. **Token Refresh Lifecycle:**
   - Prior to making any Google API call, verify `token_expires_at`.
   - If `datetime.now(timezone.utc) + timedelta(minutes=5) >= token_expires_at`, trigger Google token refresh using the encrypted `refresh_token`.
   - Re-encrypt and store updated `access_token` and `token_expires_at`.
5. **Secure Revocation on Disconnect:**
   - Disconnecting an account must send a revocation request to `https://oauth2.googleapis.com/revoke?token={token}`.
   - Securely purge all encrypted tokens, watch subscriptions, and message caches from the database.
